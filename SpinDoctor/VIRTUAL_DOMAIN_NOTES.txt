QuettaFLOP: whole virtual-domain transitions

The complete original domain is retained:
  5,000,000,000,000,000,000,000,000 virtual lanes
  10,000,000,000,000,000,000,000,000 virtual multiply/add operations per epoch

A virtual domain can be represented by a procedural definition instead of an
array containing every lane's operands and results. The canonical TQL-1
function determines a,b,c for any (word identity, lane address, epoch).
Every lane's product and result are consequently defined at every epoch:
  product(L,e) = a(L,e) * b(L,e)
  result(L,e) = product(L,e) + c(L,e)
This permits a domain-wide virtual epoch transition by updating the epoch
descriptor, while materializing only the values needed for display or queries.
It does not require reducing the virtual domain to the viewport size.

The new default viewer implements that execution model explicitly:
- Each session begins at a known initial epoch.
- ADVANCE ENTIRE VIRTUAL DOMAIN commits one or more successive epochs.
- The commit covers every lane address and both operations at each epoch.
- The ledger records contiguous epoch intervals, exact virtual operation
  counts, word/seed/program identity, previous commit hash and new SHA-256.
- Every displayed result and operation lookup uses the committed current epoch.
- Each operation is identified by (word identity, epoch, operation ID).
  IDs 2*L and 2*L+1 identify its multiply and add respectively.
- Grouped epoch advances are compact procedural transitions. They do not
  execute a host loop for each virtual lane or each individual grouped epoch.

The counts describe different scopes:
1. Virtual operations committed: 10^25 * committed epochs, exact BigInt count.
2. Host materializations: only the lane pairs evaluated for displayed samples,
   queried results, or verification. Each pair counts two source operations.
3. Host benchmark: separate integer-state clock and scalar FP64 diagnostic.
The main display uses counts rather than treating virtual commitments as
measured physical FLOP/s. Original derived QFLOP/s-equivalent reference values
are available in a collapsed panel, explicitly labeled as symbolic capacity.

The normal final viewport has 1,060 digits and evaluates 2,120 lane operations.
Its coarse preview evaluates another 768. These finite host calculations do
not shrink the virtual domain. Changing view range, zoom, or re-rendering does
not advance the virtual epoch. New Run Simulation sessions reset their ledger;
Replay Seed recreates the same initial commit and digit sequence. Subsequent
advance counts must also match to replay an identical later state.

The downloaded JSON contains both the whole-domain virtual commit ledger and
the current frame's exact cell ranges and sampled operand/result traces.
Verification regenerates the commit chain and displayed values. A chain is
an integrity check for the procedural model and recorded transitions; it does
not attest that the host physically executed every virtual operation.
The existing canonical evaluator has a 32-bit epoch address. Supported epochs
are 0..4,294,967,295. Advances past that boundary are rejected rather than aliasing.

An optional separate finite-execution page is included. It executes every lane
individually in an explicitly selected finite range each selected epoch, using
separate Number multiplication/addition with FP32 rounding and result buffers.
Options: 1,060 / 10,600 / 106,000 / 1,000,000 lanes and 1..100 epochs.
It reports counted finite-workload arithmetic divided by its own measured
execution time. This mode does not replace or reduce the full virtual domain.
At the default 1,060 lanes, every executed final result appears as a digit.
Larger finite runs retain every result while displaying 1,060 representatives.
Cancelled runs preserve partial counts and the last completed epoch, if any.
Exports retain every lane of the last completed finite epoch; earlier epochs
are reproducible from the canonical definition and addresses.

Quick start
- Open OPEN_SIMULATOR.html for the full virtual-domain viewer.
- Use ADVANCE ENTIRE VIRTUAL DOMAIN, then inspect digits or query operation IDs.
- Use VERIFY EPOCH COMMIT CHAIN and DOWNLOAD LEDGER JSON for accounting.
- Open OPEN_FINITE_EXECUTION.html for optional explicit CPU enumeration.
- OPEN_SYMBOLIC_LEDGER.html preserves the earlier sampler-only viewer.
- Run BOOT.cmd for verified carrier extraction and fresh host diagnostics.
Both updated TIFF/GIF carriers include the default and optional pages.

Validation reports describe exact-count, commit, tamper, replay, canonical trace,
actual JavaScript/native-canvas, finite execution and original-reader round-trip
checks. Browser layout and user-machine timing have not been verified here.
Prior regenerated outputs and the original supplied ZIP are preserved.


VXPU-1: contained virtual XPU terminal

The full 5 x 10^24-lane virtual domain is retained. The device is a procedural
execution abstraction inside the simulator, with an epoch register, domain-wide
commits, exact virtual operation counts, and canonical lane/operation queries.
Commands run locally inside the page. They do not invoke an OS terminal.

Commands:
  help                  list commands
  status                full virtual domain, epoch and counters
  registers             XPU command/last-result registers
  advance 1             advance the entire virtual domain by one epoch
  advance 1000000       commit a compact interval of one million virtual epochs
  eval 0                evaluate global lane 0 at the committed current epoch
  eval 0 1000001        query that lane at a previously committed epoch
  op 1                  evaluate operation ID 1 (lane 0's add)
  fma 13 7 2            explicitly evaluate multiply 13*7, then add 2; result 93
  verify                verify the complete virtual epoch commit chain
  clear                 clear terminal text while retaining the device state

Press Enter to execute. Up/Down recall command history. Quick buttons support
status, help, one epoch advance and lane 0 evaluation.
Replay/new Run Simulation sessions create a new domain; the XPU's live domain
reference follows that session. Terminal command counters are separate from
the resettable viewer counters.

Advance commits every lane by the common word-bound procedural epoch definition.
Queries materialize individual numeric results. Two host source arithmetic
operations are counted per lane/op query or small fma command. The virtual
operation count changes only for advance, by 10^25 times the epoch count.
Status, registers, verification, and viewing a stored trace do not add lane
multiply/add work. Each command reports its measured dispatch latency, counted
terminal host arithmetic, and virtual operations committed.

Immediate dispatch means the software accepts a compact virtual transition or
bounded numeric query synchronously; it does not promise zero elapsed time or
physical execution of 10^25 multiply/add operations at that instant. Viewport
refresh is deferred after XPU advance so command responses remain independent
of raster work. Export waits for a frame matching the committed epoch.

The language accepts only documented XPU commands. It does not evaluate arbitrary
JavaScript, run system commands, read files, or access a network from terminal
input. Result history is bounded. Numeric operands/addresses are validated.
Lane IDs: 0..5*10^24-1. Operation IDs: 0..10^25-1. Canonical epochs: 0..2^32-1;
historical queries require an epoch inside the current committed interval.

Open OPEN_SIMULATOR.html for the contained XPU console. Both updated TIFF/GIF
carriers embed it. BOOT.cmd generates fresh separate host benchmark evidence.
Optional finite CPU enumeration and the previous sampler remain separate pages.
The terminal retains exact virtual accounting and separates host materialization;
it makes no claim of physical QuettaFLOP/s hardware throughput.
